# Оценка сложности и этапы

## Итоговая оценка

Сложность: очень высокая, ориентировочно 9/10 для полной цели; 7/10 для урезанного MVP «text chat + history/memory + 3D bubble».

Причина — не сам HTTP/WebSocket, а необходимость сначала извлечь headless backend из UI-bound SoW, затем интегрировать две stateful системы с разными event loops, streaming, reconnect, существующим прозрачным Unity/X11/Wayland overlay и лицензионными границами. Дополнительные блокеры: Windows-only paths, незащищённый MCP fallback, второй LLM/prompt owner в Unity и расхождение active Assembly-CSharp с default Linux build.

Оценка разработки после стабилизации протокола:
- MVP Phase 0–4: 140–228 инженерных часов;
- полный P1 с audio/emotion/proactive/approval/Linux adapters: 220–368 базовых часов;
- с 20% запасом на Linux/Unity/регрессии: примерно 168–274 часов для MVP и 264–442 часа для полного P1.

Это не календарный прогноз одного непрерывного спринта: Unity build environment, ассеты, active player provenance, ручная UI-приёмка и лицензирование могут растянуть календарь. До завершения Phase 0 нельзя надёжно обещать нижнюю границу.

## Этапы

### Phase 0 — contract spike and headless extraction, 24–40 ч
- зафиксировать JSON schema;
- выделить Qt-independent service из `InterfaceSignals.handle_user_message`;
- добавить явный `SOW_DATA_ROOT` и проверить запуск из non-repository CWD;
- отключить tools/MCP/heartbeat/STT/TTS в MVP;
- mock server и Unity fake transport;
- проверить ClientWebSocket/Unity runtime на Linux;
- доказать ручной `hello → chat.submit → delta → completed`.

Gate: transport test и backend test без QApplication, активной модели и изменения player.

### Phase 1 — SoW adapter, 28–44 ч
- отдельный package/module;
- canonical submit path и serialized history commit;
- публикация stream/error/state events;
- reconnect-safe state snapshot;
- loopback-only bind и hardened auth;
- тесты на async boundary, duplicate events и provider errors.

Gate: локальный mock Unity-клиент видит реальный SoW response без Qt widgets.

### Phase 2 — MateEngine client, 36–60 ч
- `IMateEngineTransport`;
- lifecycle connect/disconnect;
- отключение `LLMCharacter.Chat`, Unity prompt persistence и random response paths;
- input submit/cancel;
- stream-to-bubble;
- idempotency and errors;
- no key in scene/prefab;
- null-safe `InputBubble` lifecycle.

Gate: staged player получает ответ SoW, bubble visible, повторный event не дублируется.

### Phase 3 — P1 presence, +80–140 ч
- emotion consumer и mapping;
- talking/lip-sync;
- audio mode decision;
- proactive speech;
- approval.request/decision;
- Linux adapters для idle, active-window, clipboard, screenshot, media и STT;
- controlled policy для MCP.

Gate: каждый P1 capability отдельно включается feature flag и имеет собственный acceptance evidence.

### Phase 4 — Linux acceptance, 28–44 ч
- отдельный player copy и launcher;
- provenance/hash record active vs candidate;
- bridge/transparent overlay;
- drag, workspace, edge-hide;
- chat-open crash regression;
- restart/reconnect;
- evidence bundle.

Gate: acceptance matrix green; только затем deployment candidate.

## Что может резко увеличить оценку

- Если LLMUnity нельзя аккуратно отключить без изменения scene/prefab wiring.
- Если Unity runtime не имеет стабильного WebSocket/client API в текущем build.
- Если P1 требует streaming audio files/PCM в Unity, а не SoW-side playback.
- Если workspace/edge-hide crash и chat crash имеют общий native/X11 root cause.
- Если понадобится полноценный two-way STT и tool UI.
- Если потребуется юридическое толкование противоречивых MateEngine distribution notices.
- Если active `Assembly-CSharp.dll` останется отдельной непроисхождённой вариацией относительно `Linux/builds/linux-3.4`, и её придётся восстанавливать/собирать отдельно.
