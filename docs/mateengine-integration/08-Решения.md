# Архитектурные решения

## ADR-001: SoW backend, MateEngine frontend

Статус: accepted for planning.

Причина: MateEngine остаётся 3D/overlay client. SoW должен стать backend, но текущий SoW UI-bound и не является headless backend; сначала требуется выделить Qt-independent ChatService из стандартного `InterfaceSignals.handle_user_message`. Soul Memory/history остаются за этим backend.

## ADR-002: отдельный application protocol

Статус: proposed.

SoW↔MateEngine chat events не смешиваются с ShojiBridge compositor IPC. Это позволяет отдельно диагностировать chat crash, edge/window crash и provider errors.

## ADR-003: application protocol after bind hardening

Статус: proposed.

У SoW есть FastAPI/WebSocket foundation, но текущий WebBridge bind-ится через GUI на `0.0.0.0:8000`, логирует token, использует query token и напрямую вызывает Qt widgets. Поэтому для MVP нужен отдельный loopback-only facade с session handshake, schema validation, correlation IDs, dedupe, cancel и state snapshot. Транспорт скрывается за `IMateEngineTransport`; Unix socket остаётся вариантом P1.

## ADR-004: единственный владелец памяти

Статус: accepted.

Soul Memory и chat history хранятся только в SoW backend. В MVP MateEngine не получает доступ к `.soul`, `characters.json` или prompt files. История и memory update проходят через один serialized canonical commit path; параллельные записи из UI/companion запрещены.

## ADR-005: disabled capabilities in MVP

Статус: accepted.

Qt approval banner, local OS tools, MCP, Soul Companion heartbeat, STT/TTS и proactive speech не являются частью MVP. При отсутствии P1 policy/approval controller действие возвращается как denied/unsupported. Это необходимо из-за Windows-only paths, Qt-bound approval и текущего MCP fallback без gate.
