# Архитектура

## Потоки

```text
MateEngine Unity client
  ├─ MateEngineSowClient (новый application client)
  ├─ ChatBot/InputBubble (только UI; LLMUnity Chat отключён в MVP)
  ├─ AvatarRandomMessages (отключён/visual-only в MVP)
  ├─ Animator + talking/emotion mapping (emotion — P1)
  ├─ audio playback / lip-sync (P1)
  └─ ShojiBridge + transparent window
          │ отдельный authenticated application IPC
          ▼
SoW Bridge Adapter / headless facade (новый слой)
  ├─ session/reconnect/idempotency
  ├─ protocol validation
  ├─ loopback-only binding
  ├─ canonical chat submit + serialized commit
  └─ event translation
          │ internal backend calls, без Qt widget coupling
          ▼
SoW backend layer (нужно выделить)
  ├─ стандартный chat orchestration из interface_signals.py
  ├─ AIFactory/providers: LLM transport
  ├─ PromptEngine + SoulMemoryAgent
  └─ repository для history/memory

Не является MVP backend entrypoint:
  sow_system_signals.py / Soul_Of_Waifu_System
  ├─ создаёт Qt UI/widgets
  ├─ содержит voice/call/companion control
  └─ имеет Linux/Windows-specific desktop paths
```

## Где интегрировать

### SoW
Предпочтительная новая точка: `app/utils/mateengine_bridge/` плюс выделяемый `app/backend/` или эквивалентный backend package.

Стандартный text-chat orchestration сейчас находится в `app/gui/interface_signals.py:handle_user_message`, а не в `sow_system_signals.py`. Вынести из него provider/prompt/history/memory flow в Qt-independent service. `interface_signals.py` и будущий MateEngine facade должны стать тонкими адаптерами к этому сервису.

`Soul_Of_Waifu_System`/`sow_system_signals.py` не использовать как headless entrypoint: его конструктор создаёт `SOW_System` UI и Qt layouts, а часть desktop paths определена только для Windows. В MVP не импортировать этот класс.

WebBridge уже умеет FastAPI/WebSocket, token guard и broadcast, но он заточен под web-client, напрямую трогает Qt widgets, не имеет correlation/dedupe/cancel/state snapshot и фактически запускается с `host="0.0.0.0"` на порту 8000. Переиспользовать можно только после отдельного hardening либо как transport foundation; готовым MateEngine API его не считать.

Канонические текущие storage paths SoW относительны current working directory:
- `app/configuration/settings.json`;
- `app/configuration/characters.json`, включая chat history;
- `.soul/<character>/chats/<chat>/memory/{MEMORY.md,USER.md,topics,backups,agent_logs.txt}`;
- `app/data/.soul/...` для attachments.

До реализации зафиксировать явный `SOW_DATA_ROOT`; MateEngine не пишет эти файлы.

### MateEngine
Первый вариант — отдельный `MateEngineSowClient.cs` в Linux overlay, не копировать Python код SoW.
Точки существующего клиента:
- `LLMUnitySamples/ChatBot.cs` — текущий active Linux/overlay manual input seam, но его прямой `LLMCharacter.Chat` должен быть отключён в MVP и заменён SoW client callback;
- `LLMUnitySamples/InputBubble.cs` — активация InputField; текущий `FixCaretSorting()` всё ещё содержит null dereference без проверки `GameObject.Find`, поэтому null-safe fix нужно сначала реализовать и отдельно протестировать;
- `AISystemPromptBinder.cs` — текущая runtime prompt file wiring; отключить live-save в MVP, чтобы `ZomeAI_prompt.txt` не стал вторым источником истины;
- `AvatarRandomMessages.cs` — независимые локализованные bubbles; отключить в MVP либо явно оставить только visual-only idle messages, не пересекающиеся с SoW events;
- `AvatarBubbleHandler.cs` — attach bubble визуального поведения;
- `AvatarHideHandler.cs` — edge-hide/window movement, не связывать с chat transport;
- `ShojiBridge.cs` — compositor IPC, не смешивать с SoW chat protocol.

Ollama path из `Assets/ollama-unity` не является active runtime path Linux overlay: он отсутствует в Linux/overlay, а старый `ChatOllama` отключён в основной сцене. Проектировать integration вокруг Ollama нельзя.

## Транспорт: решение для MVP

Рекомендуемый первый транспорт — отдельный WebSocket/HTTP loopback endpoint только после исправления bind/auth boundary. Текущий SoW WebBridge нельзя использовать как готовый endpoint: он запускается с `host="0.0.0.0"`, использует query-string token для WebSocket, логирует token при инициализации и напрямую управляет Qt widgets. Не использовать порт 8000 web/mobile API.

Скрыть транспорт за `IMateEngineTransport`, чтобы позднее заменить его на Unix domain socket. Для MVP нужны session handshake, bounded payloads, schema validation, `request_id`/`event_id`, dedupe, cancel и state snapshot. Token не передавать в URL и не логировать.


## Ownership

- Текст, history, memory, LLM request — SoW headless backend.
- Chat history и memory фиксируются через один canonical submit path; MateEngine не пишет storage напрямую.
- Bubble lifetime и visual layout — MateEngine.
- Текущее emotion state — SoW authoritative только после P1 event consumer; в MVP emotion wiring не считается готовым.
- `isTalking` — derivative state от MVP text stream; audio/lip-sync — P1.
- API credentials — только process environment/SoW provider path; никогда не Unity scene/prefab.
- Local plugins, OS control, Soul Companion heartbeat и MCP — disabled/default-deny в MVP.
