# Техническое задание: интеграция Soul of Waifu × MateEngine

Версия: 0.1
Статус: draft после анализа исходников
Платформа: Linux, текущая рабочая среда пользователя — Plasma/ShojiWM

## 1. Цель

Дать одному персонажу единое поведение Soul of Waifu и 3D-присутствие MateEngine: персонаж использует память, эмоциональное состояние, голос и инструменты SoW, а результат отображается через существующую 3D-модель MateEngine с прозрачным desktop-overlay, drag, edge-hide и анимациями.

## 2. Принципиальное решение

SoW остаётся backend/orchestrator, но с важным ограничением: в текущем исходнике нет headless backend. Для MVP требуется сначала выделить новый backend layer без QApplication, PyQt UI, QtWebEngine и VRM/Live2D widgets.

В MVP SoW backend владеет:
- стандартным text-chat orchestration из `app/gui/interface_signals.py:handle_user_message`;
- LLM-провайдером и prompt assembly;
- chat history и Soul Memory;
- минимальным event emission.

`Soul_Of_Waifu_System`/`sow_system_signals.py` не считать backend entrypoint: этот контур создаёт Qt UI и содержит voice/call/companion control. TTS/STT, Soul Companion heartbeat, OS tools и MCP не входят в безопасный MVP.

MateEngine остаётся Unity-клиентом:
- 3D-модель и animator state machine;
- прозрачное окно и ShojiBridge;
- перемещение, края экранов, workspace/monitor behavior;
- chat bubbles и UI-ввод;
- визуальная реакция на emotion/state;
- воспроизведение полученного аудио.

Не переносить Python-агент SoW внутрь Unity и не переносить Unity-рендеринг в Qt.

## 3. Пользовательские сценарии MVP

### UC-01 Ручной чат
1. Пользователь открывает чат MateEngine.
2. Ввод отправляется в SoW.
3. SoW формирует prompt с персонажем и памятью.
4. SoW потоково возвращает текстовые чанки и завершённое сообщение.
5. MateEngine отображает bubble, переводит аватар в talking state и получает audio/event.
6. История сохраняется в SoW; перезапуск не теряет связь с персонажем.

### UC-02 Проактивная реплика
Проактивная речь не входит в минимальный headless MVP. На P1 SoW может отправлять `speech.requested` только после отдельного включения heartbeat/policy. В MVP `speak`, `idle`, `micro_react`, `inner_thought` и `use_tool` из Soul Companion не экспортируются в MateEngine.

### UC-03 Эмоция без речи
Эмоциональное событие — P1. В MVP допускается только безопасный `state.snapshot` без запуска LLM или OS action. MateEngine меняет согласованный animator parameter/trigger, но не вызывает LLM самостоятельно.

### UC-04 Голос
Голос и TTS не входят в MVP. На P1 возможны два режима:
- SoW сохраняет/передаёт готовый PCM/WAV/OGG и MateEngine воспроизводит его;
- SoW сам воспроизводит звук, а MateEngine получает только `speech.started`/`speech.finished` для talking/lip-sync.

Выбрать режим только после измерения latency и стабильности Unity audio path.

### UC-05 Безопасный инструмент
OS tools и MCP не входят в MVP. Headless backend по умолчанию должен возвращать deny/unsupported. На P1 `approval.request` передаётся через authenticated IPC; отсутствие approval controller, истечение TTL, reconnect или mismatch сессии означают отказ.

## 4. Функциональные требования

| ID | Требование | Приоритет |
|---|---|---|
| FR-01 | Локальный IPC только на 127.0.0.1/Unix socket; внешний bind запрещён по умолчанию; существующий `WebBridge` этому требованию не соответствует без отдельной настройки | MVP |
| FR-02 | Аутентификация bridge session без хранения секрета в репозитории | MVP |
| FR-03 | Запрос chat с request_id, character_id и текстом | MVP |
| FR-04 | Потоковые события text_delta, message_completed, error | MVP |
| FR-05 | События emotion_changed, speech_started, speech_finished — только P1, не заявляются как готовая текущая capability | P1 |
| FR-06 | Команда cancel_request при закрытии/перезапуске чата | MVP |
| FR-07 | Идемпотентная обработка event_id; повтор события не дублирует bubble/audio | MVP |
| FR-08 | Reconnect с backoff и синхронизацией текущего состояния | MVP |
| FR-09 | SoW остаётся единственным владельцем chat history и Soul Memory; записи сериализуются через один canonical submit path | MVP |
| FR-10 | MateEngine не получает API key и не логирует Authorization | MVP |
| FR-11 | Ошибки backend показываются как безопасный bubble/status, player не завершается | MVP |
| FR-12 | Существующий ShojiBridge/edge-hide/drag не регрессирует | MVP |
| FR-13 | Состояние animation mapping настраивается данными, а не зашивается по именам одной модели | P1 |
| FR-14 | STT из MateEngine или микрофона передаётся в SoW единым событием; не входит в MVP | P1 |
| FR-15 | Все local и MCP tool calls проходят единый policy/approval gate; текущий MCP fallback SoW нельзя считать безопасным; tools отключены в MVP | P1 |
| FR-16 | Headless backend не импортирует/не создаёт QApplication, Qt UI, QtWebEngine, Live2D/VRM widgets и desktop heartbeat в MVP | MVP |
| FR-17 | SoW data root задаётся явно и не зависит от current working directory | MVP |

## 5. Контракт событий v0.1

Транспорт должен поддерживать JSON-сообщения с полями:

```json
{
  "protocol": "sow-mateengine/0.1",
  "event_id": "uuid",
  "request_id": "uuid-or-null",
  "type": "chat.submit",
  "character_id": "yuta",
  "payload": {"text": "Привет"}
}
```

Минимальные client→SoW events:
- `hello`
- `chat.submit`
- `chat.cancel`
- `state.request`
- `stt.final`
- `ui.visibility_changed`

Минимальные SoW→client events для MVP:
- `hello.ack`
- `chat.started`
- `chat.delta` с `text`
- `chat.completed` с `message_id`, `text`
- `state.snapshot`
- `error` с машинным `code` и безопасным `message`

P1 events, не существующие как готовый MateEngine API на момент анализа:
- `speech.started` с `speech_id`
- `speech.finished` с `speech_id`
- `emotion.changed` с `emotion`
- `approval.request` / `approval.result`

Правила:
- `event_id` уникален в пределах сессии;
- клиент подтверждает получение при необходимости, но не считает transport ACK завершением генерации;
- `chat.completed` — единственная точка фиксации полного сообщения на клиенте;
- provider/API errors не содержат ключ, полный prompt или Authorization header;
- payload для файлов/аудио в MVP не передавать в base64 без измерения; предпочесть локальный одноразовый path/stream.
- все события привязаны к `request_id`, а сервер обязан сериализовать фиксацию turn до запуска memory update.

## 6. Нефункциональные требования

- Linux-first, без Windows API в новом bridge-коде.
- Автоматическое восстановление после временного падения SoW.
- Наблюдаемость: correlation IDs, durations, event counters; секреты и личные данные редактируются.
- UI не блокируется сетевым запросом.
- Отдельные staged copies для тестов; активный player не заменяется до прохождения приёмки.
- Все изменения MateEngine должны сохранять лицензионные notices и публиковаться в открытом репозитории, если распространяется производный код.

## 7. Out of scope для MVP

- Переписывание Soul Memory.
- Замена Unity LLMUnity локальным/облачным транспортом внутри MateEngine.
- Полная синхронизация всех внутренних гормональных полей SoW.
- Экспорт модели/ассетов MateEngine в SoW.
- Управление ОС из Unity.
- Мультипользовательский режим.
- Коммерческая дистрибуция.

## 8. Критерий готовности MVP

Чистый staged запуск позволяет отправить русское сообщение из MateEngine, получить реальный ответ через SoW и увидеть его в bubble 3D-аватара; эмоциональное событие меняет animator state; после перезапуска SoW/MateEngine reconnect восстанавливается; edge-hide, drag, прозрачность и существующее рабочее поведение остаются исправными; тесты и evidence сохранены.
